# Phase 13.1: Fix MCP Connections Visibility in Chat UI - Context

**Gathered:** 2026-03-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix the visibility gap where org-wide and role-scoped MCP connections are invisible to users in the chat UI, even though the backend correctly authorizes and uses them during chat. Add source labeling to tool calls, read-only MCP visibility in settings, and enforce personalMcpEnabled guardrails on both frontend and backend.

</domain>

<decisions>
## Implementation Decisions

### MCP Display in Chat UI
- No new UI sections for listing org/role MCPs in the chat interface — they work silently in the backend
- Tool call summaries in the timeline show source labels: "(Org)" or "(Role)" next to MCP tool names
- Personal MCP tool calls show no source label — only org/role tools get labeled
- Source info delivered via tool name prefix convention (e.g., `mcp__org__tool_name`, `mcp__role__tool_name`)
- System prompt includes mention of available MCP tools and their sources so Claude is aware

### User Control over MCPs
- Org-wide and role-scoped MCPs are fully admin-controlled — users have zero toggle ability
- No on/off toggle for org/role MCPs in the chat UI or settings
- Existing `isActive` field on McpConnection handles admin enable/disable
- No mandatory/optional distinction needed — all admin MCPs are always-on when isActive=true

### Settings Modal MCP Tab
- Add read-only section ABOVE personal MCPs showing org-wide and role-scoped MCPs
- Read-only section shows: connection name, status indicator (connected/disconnected), tool count, server URL, source badge (Org/Role)
- When `personalMcpEnabled = false` on user's role: show personal section disabled with message ("Personal MCP connections are not enabled for your role. Contact your admin.")
- Three separate API endpoints:
  - `GET /api/mcp/connections` — Personal MCPs (existing, CRUD)
  - `GET /api/mcp/org` — Org-wide MCPs visible to current user (new, read-only)
  - `GET /api/mcp/role` — Role-scoped MCPs for current user's role (new, read-only)

### Permission Guardrails
- Frontend checks `personalMcpEnabled` flag from existing auth/session data (add to /api/auth/me response if not present)
- Backend enforces `personalMcpEnabled` on personal MCP CRUD routes — return 403 if role disables it
- Existing personal MCPs kept in database when flag is disabled, just hidden from UI
- Defense in depth: frontend hides UI, backend blocks API calls, chat route excludes from tool list

### Error Handling
- Silent fallback for org/role MCP failures — existing tool error display (red XCircle + error text) works for all MCP types
- Source label (Org/Role) appears alongside error states so users know which admin-managed tool failed
- No proactive MCP health checks before sending messages

### Chat Route Data Flow
- Backend auto-includes org-wide + role-scoped MCPs regardless of activeMcpIds sent by frontend
- Frontend activeMcpIds only controls personal MCPs
- Admin MCPs cannot be bypassed by frontend — backend is source of truth
- Source tagging via tool name prefix flows through Vercel AI SDK streaming naturally

### Schema Changes
- Add explicit `source` enum column to McpConnection model: `ORG | ROLE | PERSONAL`
- Requires Prisma schema update and database migration
- Backfill existing connections: derive from userId/roleId fields (userId=null + roleId=null → ORG, roleId set → ROLE, userId set → PERSONAL)

### API Security
- New `/api/mcp/org` and `/api/mcp/role` endpoints use `requireOrgAuth` for tenant scoping
- Return: name, status, isActive, serverUrl, available tools list, tool count
- Hide: authType, authCredentialsEncrypted, sessionId (sensitive connection details)

### Claude's Discretion
- Exact tool name prefix format (e.g., `mcp__org__` vs `mcp_org_` — whichever works best with Anthropic tool naming)
- System prompt wording for MCP tool awareness
- Read-only MCP card styling in settings (compact card vs simple list)
- Error message text for disabled personal MCP section

</decisions>

<specifics>
## Specific Ideas

- "Without affecting the current chat UI just improve the UX visuals" — minimal changes to existing chat flow
- Tool call source labels should be subtle, not prominent — blend with existing summary text style
- The approach is "backend does the heavy lifting, frontend reflects it"
- Production-grade: defense in depth on personalMcpEnabled (UI + API + chat route)

</specifics>
