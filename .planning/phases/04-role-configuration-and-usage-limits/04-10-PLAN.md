<objective>
Fix two compounding issues that prevent usage-limit enforcement from working for org users on the chat page:

1. Flat API paths (/api/conversations, /api/chat, /api/mcp/connections) carry no org slug in the URL. requireOrgAuth() calls resolveOrgSlug() which only matches /api/org/:slug/* patterns and returns null for flat paths, causing 400 "Organization context required" for ALL org member API calls. Fix: add a session-based fallback — look up organizationId from the validated session record when resolveOrgSlug returns null.

2. UsageBanner in ChatContent is gated by `{orgSlug && !isWelcomeVisible && <UsageBanner />}`. Since conversations fail to load (due to root cause 1), isWelcomeVisible stays true permanently, the banner never mounts, onBlockedChange never fires, and usageBlocked stays false. Fix: always mount UsageBanner when orgSlug is set; suppress the visual output only (via CSS hidden class) when on the welcome screen.

Purpose: UCHAT-03, UCHAT-04, OUSE-02, OUSE-03, SAFE-10 — usage limit enforcement is the core Phase 4 chat-blocking requirement. Without this fix, blocked users can still send messages.
Output: lib/auth-middleware.ts with session-based org fallback; components/full-chat-app.tsx with UsageBanner always mounted.
</objective>

<task type="auto">
  <name>Task 1: Add session-based org fallback to requireOrgAuth</name>
  <files>lib/auth-middleware.ts</files>
  <action>
In requireOrgAuth(), after `resolveOrgSlug(req)` returns null, fall back to looking up the org from the session's organizationId field instead of immediately returning 400.

The session is already validated at step 1 (auth.sessionId is available). Use the session token from the Authorization header to fetch the full session including organizationId, then look up the org by ID.

Concrete change — replace the current "return 400 if no slug" block:

```typescript
// CURRENT (broken):
const slug = resolveOrgSlug(req);
if (!slug) {
  return NextResponse.json({ error: 'Organization context required' }, { status: 400 });
}
// QUERY uses: where: { userId: user.id, organization: { slug, deletedAt: null, status: 'ACTIVE' } }
```

With a dual-path approach:

```typescript
const slug = resolveOrgSlug(req);

// For flat /api/* paths (no slug in URL), fall back to session organizationId
let orgMember: ... | null = null;

if (slug) {
  // Path A: slug from URL (e.g., /api/org/:slug/... routes)
  orgMember = await prisma.orgMember.findFirst({
    where: {
      userId: user.id,
      organization: {
        slug,
        deletedAt: null,
        status: 'ACTIVE',
      },
    },
    include: { organization: true, role: true },
  });
} else {
  // Path B: no slug in URL — resolve org from session.organizationId
  // Fetch the session to get organizationId (auth.sessionId is already known)
  const sessionRecord = auth.sessionId
    ? await prisma.session.findUnique({
        where: { id: auth.sessionId },
        select: { organizationId: true },
      })
    : null;

  const orgId = sessionRecord?.organizationId ?? null;
  if (!orgId) {
    return NextResponse.json({ error: 'Organization context required' }, { status: 400 });
  }

  orgMember = await prisma.orgMember.findFirst({
    where: {
      userId: user.id,
      organizationId: orgId,
      organization: {
        deletedAt: null,
        status: 'ACTIVE',
      },
    },
    include: { organization: true, role: true },
  });
}
```

After this change, the existing `if (!orgMember)` 403 guard handles both paths identically. No other logic in requireOrgAuth needs to change.

The forcePasswordChange redirect at step 5b references `slug` in the redirect URL. When slug is null (session path), derive it from orgMember.organization.slug after the orgMember lookup:

// In forcePasswordChange guard (step 5b), replace the hardcoded slug with:

redirectTo: `/org/${resolvedSlug}/force-password-change`,

Do NOT change resolveOrgSlug itself — the fix lives entirely in requireOrgAuth. Do NOT change any API route files — they all call requireOrgAuth which self-heals with this fix.
