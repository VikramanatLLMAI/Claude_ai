# Phase 13.1: Fix MCP Connections Visibility in Chat UI - Research

**Researched:** 2026-03-09
**Domain:** MCP connection visibility, tool source labeling, permission guardrails
**Confidence:** HIGH

## Summary

This phase fixes a visibility gap where org-wide and role-scoped MCP connections work silently in the backend but are invisible to users. The existing code already has the critical backend logic: the chat route (lines 150-167) queries all three tiers of MCP connections (org-wide, role-scoped, personal). However, it only loads tools that the frontend explicitly sends via `activeMcpIds` -- meaning org/role MCPs are authorized but never actually loaded unless a user manually knows and sends their IDs.

The fix requires: (1) auto-including org/role MCPs on the backend regardless of `activeMcpIds`, (2) source-prefixing tool names so the frontend can display labels, (3) adding read-only MCP visibility in the settings modal, (4) enforcing `personalMcpEnabled` as a defense-in-depth guardrail, and (5) adding an explicit `source` enum to the McpConnection schema.

**Primary recommendation:** Backend-first approach -- fix the chat route to auto-include org/role MCPs with source-prefixed tool names, then layer on frontend visibility changes.

### Tool Name Prefix Convention

**Recommendation: Use `mcp__org__` and `mcp__role__` double-underscore prefixes.**

Rationale:
- Anthropic API tool names allow alphanumeric + underscores, max 64 chars
- Existing convention uses single underscore: `mcp_toolname`
- Double underscore creates unambiguous delimiter: `mcp__org__toolname` vs `mcp__role__toolname`
- Personal MCPs keep existing: `mcp_toolname` (no source label needed per decisions)
- Frontend regex parsing: `/^mcp__(org|role)__(.+)$/` cleanly extracts source and original name
- 64-char limit: `mcp__org__` = 10 chars, `mcp__role__` = 11 chars, leaving 53-54 chars for tool name

**Confidence:** HIGH -- verified Anthropic allows underscores in tool names, existing code already uses `mcp_` prefix pattern.

### Schema Change: McpConnection.source

```prisma
enum McpSource {
  ORG
  ROLE
  PERSONAL
}

model McpConnection {
  // ... existing fields
  source  McpSource @default(PERSONAL)
  // ... rest
}
```

**Backfill logic:**
- `userId IS NULL AND roleId IS NULL` -> `ORG`
- `userId IS NULL AND roleId IS NOT NULL` -> `ROLE`
- `userId IS NOT NULL` -> `PERSONAL`

This is a denormalization for query clarity. The source can always be derived from userId/roleId but having it explicit makes queries cleaner and enables the API endpoints to filter by source directly.

### New API Endpoints

**`GET /api/mcp/org`** -- Org-wide MCPs visible to current user
- Auth: `requireOrgAuth(req)`
- Query: `tenantDb.mcpConnection.findMany({ where: { source: 'ORG', userId: null, roleId: null } })`
- Response: sanitized (no credentials, no sessionId)

**`GET /api/mcp/role`** -- Role-scoped MCPs for current user's role
- Auth: `requireOrgAuth(req)` -- provides role info
- Query: `tenantDb.mcpConnection.findMany({ where: { source: 'ROLE', roleId: role.id } })`
- Response: sanitized

### Chat Route Modification

The key change in `app/api/chat/route.ts`:

```typescript
// BEFORE: Only load what frontend sends
const filteredMcpIds = (activeMcpIds || []).filter(id => authorizedMcpIds.has(id));

// AFTER: Separate by source, auto-include org/role
const authorizedMcpConnections = await tenantDb.mcpConnection.findMany({
  where: {
    isActive: true,
    OR: [
      { source: 'ORG' },                                    // Org-wide (always)
      { source: 'ROLE', roleId: role.id },                   // Role-specific (always)
      ...(role.personalMcpEnabled
        ? [{ source: 'PERSONAL', userId: user.id }]          // Personal (if role permits)
        : []),
    ],
  },
  select: { id: true, source: true },
});

// Org/role MCPs: always loaded (not filtered by activeMcpIds)
const orgRoleMcpIds = authorizedMcpConnections
  .filter(c => c.source === 'ORG' || c.source === 'ROLE')
  .map(c => c.id);

// Personal MCPs: only those the frontend activated
const personalMcpIds = new Set(
  authorizedMcpConnections.filter(c => c.source === 'PERSONAL').map(c => c.id)
);
const filteredPersonalMcpIds = (activeMcpIds || []).filter(id => personalMcpIds.has(id));

// Load all with source-appropriate prefixes
const allMcpIds = [...orgRoleMcpIds, ...filteredPersonalMcpIds];
```

- Org MCP tools: `mcp__org__toolname`

### Frontend Tool Name Parsing

In `tool-timeline.tsx` and `tool.tsx`, the `formatToolName` function needs source-aware parsing:

```typescript
function parseToolSource(name: string): { source: 'org' | 'role' | null; cleanName: string } {
  const match = name.match(/^mcp__(org|role)__(.+)$/);
  if (match) {
    return { source: match[1] as 'org' | 'role', cleanName: match[2] };
  }
  return { source: null, cleanName: name };
}

function formatToolName(name: string): string {
  const { cleanName } = parseToolSource(name);
  // Use cleanName for display (strip mcp_ prefix from personal too)
  const displayName = cleanName
    .replace(/^mcp_/, "")
    .replace(/_/g, " ")
    .replace(/([A-Z])/g, " $1")
    .replace(/\b\w/g, c => c.toUpperCase())
    .trim();
  return displayName;
}
```

## Common Pitfalls

### Pitfall 1: Tool Name Collision
**What goes wrong:** Two MCP connections (one org, one personal) expose a tool with the same name, causing key collision in the tools object.
**Why it happens:** `Object.assign(tools, mcpTools)` overwrites duplicates silently.
**How to avoid:** Source prefix (`mcp__org__`, `mcp__role__`, `mcp_`) ensures unique keys even for same-named tools across sources.
**Warning signs:** Tool calls silently use wrong connection.

### Pitfall 2: Breaking Existing Tool Display
**What goes wrong:** The `formatToolName` function strips `mcp_` prefix but doesn't know about `mcp__org__` prefix, showing garbled names like `_org__toolname`.
**Why it happens:** Existing regex `replace(/^mcp_/, "")` only removes single `mcp_`.
**How to avoid:** Update `formatToolName` in BOTH `tool.tsx` and `tool-timeline.tsx` to handle new prefix pattern before the old strip logic.
**Warning signs:** Tool names in timeline show underscore-heavy garbled text.

### Pitfall 3: Chat Route Regression for Users Without MCP
**What goes wrong:** Users with no MCP connections get errors because the code assumes some MCP data exists.
**Why it happens:** Adding source-based filtering changes the query structure.
**How to avoid:** Empty array handling -- if no authorized MCPs, skip the entire MCP tool loading block (existing pattern).

### Pitfall 4: Tenant Isolation on New Endpoints
**What goes wrong:** `/api/mcp/org` returns MCPs from other orgs.
**Why it happens:** Forgetting to use `tenantDb` (which auto-filters by org).
**How to avoid:** Always use `requireOrgAuth` and the returned `tenantDb` for queries. Never use raw `prisma`.

### Pitfall 5: Backfill Script Race Condition
**What goes wrong:** Schema deployed with `source` column but backfill not run, so all existing connections have `PERSONAL` default.
**Why it happens:** Prisma enum defaults to first value or specified default.
**How to avoid:** Set default as `PERSONAL` (correct for most connections), run backfill as part of migration to fix org/role ones.

## Open Questions

1. **Tool name length with prefix**
   - What we know: Anthropic allows max 64 chars for tool names. Prefix adds 10-11 chars.
   - What's unclear: Whether any existing MCP tools have names approaching 53 chars.
   - Recommendation: Truncate tool names if prefix + name exceeds 64 chars. Log a warning. LOW risk.

2. **MCP tool loading order with source map**
   - What we know: `loadActiveMcpToolsWithDescriptions` processes connections sequentially.
   - What's unclear: Whether the function signature change is backward-compatible for any other callers.
   - Recommendation: Make `sourceMap` optional (default undefined) for backward compatibility. Only the chat route passes it.
