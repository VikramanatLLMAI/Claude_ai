**Fix 1: Organization dialog state bug (UAT Test 5)**

The issue: After opening Edit dialog (sets `editingOrg` + `formOpen=true`), closing via X calls `onOpenChange(false)` which sets `formOpen=false` and then `editingOrg=null`. The problem is that the Radix Dialog animation closing + React state batching can cause a brief flash where `formOpen` becomes `true` again (Radix Dialog calls `onOpenChange(true)` during close animation) while `editingOrg` is being cleared.

In `app/super-admin/organizations/page.tsx`, the Edit click handler (line 503-506):
```typescript
<DropdownMenuItem onClick={() => {
  setEditingOrg(org)
  setFormOpen(true)
}}>
```

And the dialog (line 579-587):
```typescript
<OrgFormDialog
  open={formOpen}
  onOpenChange={(open) => {
    setFormOpen(open)
    if (!open) setEditingOrg(null)
  }}
  org={editingOrg}
  onSubmit={editingOrg ? handleEdit : handleCreate}
/>
```

The fix: Change the `onOpenChange` to clear `editingOrg` BEFORE setting `formOpen` to false, or better yet, don't pass `formOpen` as the `open` prop — derive it from `editingOrg` for Edit mode and a separate `showCreate` flag for Create mode. Simplest fix:

Replace the dialog state with a single discriminated union approach:
```typescript
const [dialogMode, setDialogMode] = React.useState<'closed' | 'create' | 'edit'>('closed')
const [editingOrg, setEditingOrg] = React.useState<Organization | null>(null)
```

Or simpler: just ensure `editingOrg` is cleared synchronously when closing:
```typescript
<OrgFormDialog
  open={formOpen}
  onOpenChange={(open) => {
    if (!open) {
      setEditingOrg(null)
    }
    setFormOpen(open)
  }}
  org={editingOrg}
  onSubmit={editingOrg ? handleEdit : handleCreate}
/>
```

And in the OrgFormDialog's `onSubmit` success handler (around line 144), also clear the editingOrg:
```typescript
// After successful submit
onOpenChange(false) // This will clear editingOrg via the parent handler
```

Also add a guard in the OrgFormDialog: if `!open` reset internal form state. The issue is likely that when the Edit dialog closes, the internal form retains the edit data, and then the Create button opens `formOpen=true` with stale form data. Fix by resetting form state in a `useEffect` when `open` changes:

```typescript
React.useEffect(() => {
  if (open) {
    // Reset form when dialog opens
    setName(org?.name ?? '')
    setSlug(org?.slug ?? '')
    // ... other fields
  }
}, [open, org])
```

**Fix 3: API key mask format (UAT Test 10)**

In `lib/services/api-key-service.ts`, the `maskKey` function (line 74-79):
```typescript
function maskKey(rawKey: string): string {
  if (rawKey.length <= 11) {
    return rawKey.slice(0, 4) + '...';
  }
  return rawKey.slice(0, 7) + '...' + rawKey.slice(-4);
}
```

This looks correct — `slice(0, 7)` returns the first 7 characters. The UAT tester reported seeing 6 chars. Possible causes:
1. The key stored in the DB has a different format than expected
2. The decryption produces a slightly different result
3. The `(decryption error)` fallback (line 110) produces a short string that masks differently

**Important:** This maskKey function is in the SERVICE file, not the page file. The `formatApiKey` function (line 84) decrypts the key and then masks it. If decryption fails, `rawKey = '(decryption error)'` (17 chars), which would produce `(decryp...ror)` — 7 chars + ... + 4 chars = correct.

The most likely issue: if the actual Anthropic API key starts with `sk-ant-api03-` (which is the current format), counting characters: `s-k---a-n-t-` is already 7 characters for `sk-ant-`. Wait — `sk-ant-` is 7 chars. If the tester counted the visible prefix and it showed `sk-ant` (6 chars), then `slice(0, 7)` would give `sk-ant-` (7 chars including the dash). The tester may have miscounted, OR the key format starts differently.

Verify by checking the actual masked output in the database/UI. If the mask IS showing 7 chars, this is a non-issue. If it's showing 6, check if there's a different maskKey function being used elsewhere, or if the frontend is truncating.

If the maskedKey in the API response has the correct 7-char prefix, the issue is frontend display (CSS overflow or font rendering). Check the MaskedKeyCell component for any text truncation styles.
