<diagnosis>
**Likely root causes to investigate at runtime:**

1. **ensureMinimumSuperAdmins() returns false**: The function checks `count > 1` — if there are exactly 2 SAs and one is being deleted, this returns true. But there might be a race condition or the count query could be failing.

2. **Transaction failure**: The `deleteSuperAdmin` function uses `prisma.$transaction()`. Inside it:
   - `tx.session.deleteMany({ where: { userId } })` — if the Session model has changed or the userId FK doesn't match, this could throw.
   - `tx.user.delete({ where: { id: userId } })` — if there are FK constraints preventing deletion (e.g., the user has AuditLog records referencing them, or OrgMember records), this would throw a Prisma constraint error.

3. **Foreign key constraint violation**: The User model likely has relations to AuditLog (userId), Session, etc. If cascade delete isn't configured for these relations, `user.delete()` will fail with a foreign key constraint error. This is the most likely cause — audit logs reference the SA user, preventing deletion.

4. **The `deleteSuperAdmin` function catches nothing**: The function has no try-catch. Errors propagate to the route handler, which only checks for specific error messages ("Cannot delete yourself", "At least", "last Super Admin", "not found"). A Prisma constraint error wouldn't match any of these, falling through to the generic 500.

The executor should check the actual runtime error message to confirm which cause it is, then fix accordingly.
</diagnosis>

**Step 2: Fix based on captured error.**

**If FK constraint violation (most likely):**
The User model has relations to AuditLog, Session, and potentially other models. When deleting a Super Admin user, all referencing records must be handled first.

In `deleteSuperAdmin()` in `lib/services/super-admin-service.ts`, update the transaction to delete or nullify all dependent records before deleting the user:

```typescript
return await prisma.$transaction(async (tx) => {
  const user = await tx.user.findUnique({
    where: { id: userId, isSuperAdmin: true },
    select: { id: true, email: true, name: true },
  });
  if (!user) {
    throw new Error('Super Admin not found');
  }

  // Delete all their sessions
  await tx.session.deleteMany({ where: { userId } });

  // Nullify audit log references (audit logs are immutable per SAFE-07, but we can null the userId)
  // OR if the schema uses SET NULL on the relation, this may not be needed
  // Check the AuditLog model's userId relation — if it's required (not nullable), we need to handle it
  await tx.auditLog.updateMany({
    where: { userId },
    data: { userId: null as any }, // Only if userId is nullable in schema
  });

  // Delete the user
  await tx.user.delete({ where: { id: userId } });

  await auditLog.record(tx, {
    userId: actorId,
    action: 'super_admin.deleted',
    targetType: 'User',
    targetId: userId,
    ipAddress,
    metadata: { email: user.email, name: user.name },
  });

  return { success: true, deletedUser: user };
});
```

**IMPORTANT:** Check `prisma/schema.prisma` for the AuditLog model's `userId` field. If it's `userId String @map("user_id")` (required, non-nullable), you need to either:
- Make it nullable in the schema (`userId String? @map("user_id")`) and run `npm run db:push`, then nullify before delete
- Or use `onDelete: SetNull` on the relation
- Or delete the audit logs for that user (but this violates SAFE-07 immutable audit logs)

The best approach: Make AuditLog.userId nullable (it makes sense — the user record can be deleted but the audit trail should remain with a null userId indicating a deleted user). Then nullify the userId in audit logs before deleting the user.

**If Prisma client out of sync:** Run `npm run db:generate` then retry.
