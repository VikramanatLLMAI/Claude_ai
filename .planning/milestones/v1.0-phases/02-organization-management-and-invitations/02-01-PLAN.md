**Step 1: Create lib/services/org-service.ts**

All functions use `prisma.$transaction()` for atomicity with audit logging. Import `prisma` from `@/lib/db`, `auditLog` from `./audit-service`, and `DEFAULT_ROLE_TEMPLATES` from `@/lib/constants/role-templates`.

Functions to implement:

1. **`createOrganization(data, actorId, ipAddress)`** — SORG-01
   - Accepts: `{ name, slug, logoBase64?, logoDisplayMode?, initialAdminEmail? }`
   - Wraps everything in `prisma.$transaction()`:
     a. Create Organization record
     b. Create 3 system roles from DEFAULT_ROLE_TEMPLATES (loop over templates, create each Role with `organizationId: org.id`)
     c. Create OrgSettings with `defaultRoleId` set to the Basic role's id, `conversationVisibility: false` (ODEF-01)
     d. Create PasswordPolicy with defaults (just `organizationId: org.id`)
     e. If `initialAdminEmail` provided: find the "Technical" role (for Org Admin), create Invitation with `token: generateToken()`, `status: 'PENDING'`, `expiresAt: 7 days from now`, `invitedById: actorId`
     f. Audit log: `action: 'org.created'`, metadata includes org name, slug, and whether initial invite was sent
   - Handle slug uniqueness violation (Prisma P2002 error code) — throw descriptive error "Organization with this slug already exists"
   - Return: org record with roles and settings

2. **`updateOrganization(orgId, data, actorId, ipAddress)`** — SORG-02
   - Load current org state first (for before/after in audit log)
   - Update name, slug, logoDisplayMode (only provided fields)
   - Handle slug uniqueness violation (P2002)
   - Audit log with before/after snapshot

3. **`suspendOrganization(orgId, actorId, ipAddress)`** — SORG-03
   - Check org exists and is ACTIVE (throw if already suspended)
   - Update status to 'SUSPENDED'
   - **Delete all sessions for this org**: `tx.session.deleteMany({ where: { organizationId: orgId } })` — immediate effect per CONTEXT.md
   - Audit log: `action: 'org.suspended'`

4. **`activateOrganization(orgId, actorId, ipAddress)`** — SORG-04
   - Check org exists and is SUSPENDED (throw if already active)
   - Update status to 'ACTIVE'
   - Audit log: `action: 'org.activated'`

5. **`deleteOrganization(orgId, actorId, ipAddress)`** — SORG-05, SAFE-05
   - Check org exists and is not already deleted (deletedAt is null)
   - SAFE-04: This function does NOT check if actor is Org Admin of this org — that check is handled at the API route level (only Super Admin can call this)
   - Set `deletedAt: new Date()` — soft delete, NOT hard delete
   - Audit log: `action: 'org.deleted'`

6. **`restoreOrganization(orgId, actorId, ipAddress)`** — SAFE-05
   - Check org exists and IS deleted (deletedAt is not null)
   - Check within 30-day grace period: `deletedAt > new Date(Date.now() - 30 * 24 * 60 * 60 * 1000)`
   - Set `deletedAt: null`
   - Audit log: `action: 'org.restored'`

7. **`listOrganizations()`** — SORG-06
   - Fetch all orgs (including soft-deleted for "Pending Deletion" display per CONTEXT.md)
   - Include aggregations: `_count: { members: true }` for user count
   - For soft-deleted orgs, calculate `daysRemaining = 30 - daysSinceDeleted`
   - Order by: status (ACTIVE first), then name
   - Return array with org data + userCount + daysRemaining (null if not deleted)

8. **`getOrganization(orgId)`**
   - Fetch single org with member count, roles, settings
   - Return null if not found

9. **`updateOrgLogo(orgId, logoBase64, actorId, ipAddress)`** — SORG-07
   - Update `logoBase64` field
   - Audit log: `action: 'org.logo_updated'` (do NOT include the base64 data in the audit log metadata — just log that it changed)

**Step 3: Create lib/services/role-template-service.ts**

System role templates are stored as hardcoded constants (DEFAULT_ROLE_TEMPLATES). Since there is no SystemRoleTemplate table in the schema, use a pragmatic approach:

Store template overrides in a JSON file or use a simple key-value mechanism. Given the research's open question and the constraint that we should not add new tables to the schema in this phase, implement templates as:

- **getTemplates()**: Return DEFAULT_ROLE_TEMPLATES as the source of truth. If a `platform_settings` record exists in a future phase, merge overrides. For now, just return the constants.
- **getTemplate(name)**: Find by name in DEFAULT_ROLE_TEMPLATES.
- **updateTemplate(name, data, actorId, ipAddress)**: For v1, template editing means updating the constants file at runtime is not possible. Instead, store overrides in the AuditLog metadata pattern... Actually, this is too complex.

**Pragmatic approach (per research recommendation):** Templates are managed entirely through the constants file. The "edit" API simply validates the input and returns success — the actual template data in `lib/constants/role-templates.ts` is the master copy. For Phase 2, Super Admin can VIEW templates and RESET them. Full template editing (STPL-02) stores overrides — but since we need this to work without schema changes, store template overrides as a JSON file at `.data/role-templates.json` that gets merged with defaults at read time. If the file doesn't exist, defaults are used. Reset deletes the override entry.

Implementation:
- Use `fs.readFileSync/writeFileSync` with a `.data/role-templates.json` file for overrides
- `getTemplates()`: Read defaults, merge any overrides from JSON file
- `getTemplate(name)`: Same but single template
- `updateTemplate(name, data, actorId, ipAddress)`: Write override to JSON file, audit log
- `resetTemplate(name, actorId, ipAddress)`: Remove override from JSON file, audit log
- Ensure `.data/` directory is gitignored
- Audit log calls use the global `prisma` (not transaction) since templates are not in a DB table

Add `.data/` to `.gitignore` if not already present.
