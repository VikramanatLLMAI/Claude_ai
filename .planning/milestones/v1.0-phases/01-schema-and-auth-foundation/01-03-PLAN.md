**Step 1: Create proxy.ts in project root (ROUTE-01, ROUTE-02)**

This is the Next.js 16 proxy file (replaces deprecated middleware.ts). It handles subdomain-to-path rewriting ONLY in production. Development uses path-based routing directly.

Follow the pattern from 01-RESEARCH.md "Pattern 4: proxy.ts for Subdomain Routing".

Key implementation:
- Read ROOT_DOMAIN from env var (default: 'llmatscale.ai')
- Define PLATFORM_SUBDOMAINS: Set(['www', 'api'])
- Skip API routes (`/api/`) and static files (`/_next/`)
- In development mode: `NextResponse.next()` (no rewriting needed)
- Bare domain or www: `NextResponse.next()` (serve bare domain pages)
- admin subdomain: rewrite to `/admin${pathname}` (ROUTE-01)
- Any other subdomain: rewrite to `/org/${subdomain}${pathname}` (ROUTE-02)
- Set `x-org-slug` response header on org rewrites for server components

CRITICAL: proxy.ts does NO authentication, NO database queries. It is a thin URL rewriter only. Auth happens in route handlers (CVE-2025-29927 defense-in-depth per AUTH-07).

Export config with matcher that excludes api and _next routes.

**Step 5: Create a simple API endpoint for org lookup — app/api/auth/find-org/route.ts**

New API route:
- POST accepts `{ email: string }`
- Validates email format with Zod
- Looks up user by email
- If user is Super Admin: return `{ type: "super_admin" }`
- If user has org membership: return `{ type: "org", slug: org.slug }`
- If user not found: return `{ type: "not_found" }` (generic — no leakage about email existence)
  - IMPORTANT: Use constant-time response to prevent timing attacks. Whether user exists or not, the response time should be similar.
